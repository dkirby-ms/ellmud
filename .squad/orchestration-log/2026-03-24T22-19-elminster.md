## Summary

Reviewed the Entra External ID OAuth implementation against stated architectural intent. **Finding: The architecture is correctly scoped — Entra is identity provider only, no API protection, all roles managed in Postgres.** The failures in local dev and UAT are **configuration and implementation bugs, not architectural problems.**

## Key Findings

1. **Architecture is correct** — Entra login flow → find-or-create player → issue own session token. No Entra access tokens stored, no Entra APIs called post-login, no Entra role claims consumed.

2. **Bug 1: Redirect URI mismatch** — `.env.example` documents `/auth/callback`, but server route is `/auth/entra/callback`. OAuth code never exchanges.

3. **Bug 2: Tenant ID vs. subdomain confusion** — `EntraAuthService.ts` builds CIAM issuer URL with tenant GUID as subdomain: `{GUID}.ciamlogin.com` → DNS failure. Should use tenant subdomain name (e.g., `contoso`).

4. **Minor issues identified:**
   - Token passed in URL query params (security hygiene)
   - Entra config reads from `process.env` instead of centralized `config.ts`
   - `ENTRA_CLIENT_SECRET` as plain env var in Container Apps (should use Key Vault ref)

5. **Correct patterns confirmed:**
   - `EntraAuthService` OIDC flow is correct and minimal
   - `AuthService.loginOAuth()` find-or-create pattern is correct
   - `colyseus-auth.ts` validates own tokens only (correct)
   - Database schema already supports OAuth
   - `openid-client` v6 is the right library choice
