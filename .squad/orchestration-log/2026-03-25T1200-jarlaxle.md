## Work Summary

### Investigation Scope
- User account Postgres persistence
- Game profile data persistence (skills, faction, stash)
- Auth flow vs. profile flow decoupling
- ShardRoom player state initialization and tracking

### Findings

#### ✅ What Works
1. `PgPlayerRepository` — Creates real user accounts with bcrypt password hashing
2. `PgStashRepository` — Persists stash items to DB when DATABASE_URL is configured
3. Auth flow — Registration/login writes to `players` and `player_identities` tables
4. Stash transfer in extraction — Items move between game world and stash (in-memory), persisted if DB available

#### ❌ Critical Gap: ShardRoom sessionId Bug
- **Location:** ShardRoom.onJoin() line 206
- **Issue:** PlayerState is keyed to ephemeral `client.sessionId` instead of authenticated `playerId`
- **Contrast:** RefugeRoom correctly resolves `playerId` from auth context (line 91)
- **Impact:** On reconnect, player gets new sessionId → stash data from previous session becomes inaccessible (data exists in DB but orphaned by session key)
- **Status:** CRITICAL — Blocks stash persistence
- **Fix Pattern:** Mirror RefugeRoom's playerId resolution in ShardRoom.onJoin()

#### ❌ Major Gap: No Profile Persistence
1. **Missing Repository:** PlayerProfileRepository doesn't exist
2. **Missing Service:** No service layer to load/save skills, faction, carry weight
3. **Tables Empty:** player_skills, faction_membership, run_history tables defined in schema but never written
4. **Fresh State Every Join:** PlayerState initialized with hardcoded defaults every shard join, never reads from DB

#### ❌ Major Gap: No Save/Load Cycle
1. **On Join:** PlayerState created with defaults (stealth: 5, awareness: 5)
2. **On Leave:** No profile data written back to DB
3. **Result:** Skills reset on every disconnect/reconnect
