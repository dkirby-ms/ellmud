## Summary

Implemented server-driven, client-executed room switching between Refuge and Shard via `ROOM_SWITCH` message type. Server authorizes transitions; client handles disconnect/reconnect. Enables core gameplay loop: login → enter shard → extract → return to refuge.

## Changes

### Message Type Addition
- **File:** `packages/shared/src/index.ts`
- **Addition:** `ROOM_SWITCH` message type (`{ target, options?, reason }`)
- **Protocol:** Append-only; no breaking changes to existing types

### Server-Side Room Switching
- **File:** `packages/server/src/rooms/RefugeRoom.ts`
- **Feature:** `enter` command defaults to shard when no argument (Phase 1: single shard only)
- **Mechanism:** Command handler calls `switchingRef` guard; emits `ROOM_SWITCH` message with target='shard'

- **File:** `packages/server/src/rooms/ShardRoom.ts`
- **Mechanism:** Upon extraction completion, emits `ROOM_SWITCH` message with target='refuge' and reason='extraction_complete'

### Client-Side Room Switching
- **File:** `packages/client/src/services/connection.ts`
- **Feature:** `switchRoom()` method: leave current room → join target room via matchmake API
- **Guard:** No client-side routing; server dictates when and where transitions occur

- **File:** `packages/client/src/components/GameScreen.tsx`
- **Feature:** `switchingRef` guard prevents onLeave handler from showing disconnect messages during room transitions
- **Handler pattern:** `handlersRef` reusable across room switches, avoiding stale closures

## Learnings

Server-initiated, client-executed pattern ensures:
- **Server authoritative:** Only server decides when switches occur
- **Clean disconnects:** Client leaves before joining next room, preventing orphaned connections
- **Extensible:** `options` field can carry biome selection, shard tier, etc. in future phases
