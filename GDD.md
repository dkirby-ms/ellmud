# Ellmud — Game Design Document (GDD)

## Genre
PvPvE Extraction RPG · Real-Time MUD · Dual Exploration (Static + Procedural)

## Core Fantasy
You are a **Shardwalker**, diving into unstable echoes of a dying world, scavenging artifacts, outwitting monsters and other players, and escaping before the shard collapses.

## Platform
Web browser only (React + Vite client via WebSocket). Text-primary interface with modern UI components, compass navigation, and styled terminal output. Optional ANSI colour support. No graphics engine. No SSH or raw TCP support. Accessible by design.

## Target Audience
- Players who grew up on MUDs, roguelikes, or interactive fiction and want modern design sensibility
- Extraction-game fans (Tarkov, Dark and Darker, Hunt: Showdown) looking for a different medium
- Tabletop RPG players who enjoy theatre-of-the-mind combat
- Anyone drawn to emergent, high-stakes multiplayer in short sessions (20-40 min runs)

---

# 1. HIGH-LEVEL VISION

**Ellmud** blends the tension of extraction games with the imagination and readability of classic MUDs.
Players live in **the Refuge**, a persistent hub where they manage gear, prepare for runs, and socialize.
From there, they explore **two complementary exploration modes:**
- **Static zones** (like the Refuge itself, and future hand-crafted game areas) — permanent, designed environments for feature access and discovery
- **Procedurally generated "shards"** — temporary instances of corrupted regions — where they face PvE threats, environmental hazards, and emergent PvP encounters

All player-facing text is generated by an **LLM that narrates the world**, but **the world itself is deterministic and server-authoritative**.
The LLM is a *lens*, not a *game engine*.

### Design Pillars
1. **Tension through information scarcity.** You never have the full picture. Sound cues, traces, and partial descriptions force decisions under uncertainty.
2. **Meaningful risk.** Gear brought into a shard can be lost. Gear extracted is earned. No run is free.
3. **Emergent narrative.** The LLM weaves flavour around mechanical truth, so every run reads differently even when the underlying events are similar.
4. **Respect for the player's time.** Runs are 20-40 minutes. Preparation is fast. Death stings but doesn't erase weeks of progress.

# 2. GAME STRUCTURE

## 2.1 Persistent World (The Refuge)
A safe, persistent hub — "The Refuge" — implemented as a **zone** in the database with 7 interconnected rooms, where players:
- Manage their **stash** (persistent inventory stored between runs) in the **Stash Alcove**
- Equip **loadouts** from stash items
- Read **the Shardboard** in the dedicated Shardboard room (a bulletin of available shard entries and run history)
- Access the **Market** (future: player trading and faction vendors)
- Train at the **Training Grounds** (future: skill progression)
- Visit the **Infirmary** (future: debuff removal and healing services)
- Strategize in the **War Room** (future: faction headquarters)
- Socialize in the **Hearth** (central gathering area)

No combat occurs here. The Refuge serves as a **feature-room hub** — each room provides access to specific gameplay systems.

### Refuge as a Zone *(Implemented)*
The Refuge is a persistent zone (category: `hub`, lifecycle: `persistent`) defined in the database (`zones`, `zone_rooms`, `zone_exits` tables). Players navigate between rooms using standard directional commands (`go north`, `n`, etc.) or the compass UI. The RefugeRoom implementation is a long-lived Colyseus Room that persists across player sessions.

### Feature Rooms
Specific gameplay features are accessed in designated rooms:
- **Stash Alcove**: `stash`, `take`, `store` commands
- **Shardboard**: `shardboard`, `enter` commands (join shard instances)
- **Market**, **Training Grounds**, **Infirmary**, **War Room**: Reserved for future feature implementations

### Future: Ambient World Simulation *(Planned, Not Implemented)*
Future phases will add tick-driven ambient life to the Refuge:
- NPC merchants wandering between rooms
- Faction representatives and dynamic vendor appearances
- Time-of-day cycles and weather atmosphere
- Collective faction milestone events (construction projects, banner changes)

## 2.2 Instance Layer (Shards / Runs)
Each run is:
- A **room-graph** sourced from the **database zone system** (hand-crafted zones) or **dynamically assembled** from database room definitions (procedural shards). Room count varies by shard tier: 15-60 rooms.
- Populated with **creatures, hazards, loot, and traces** from database content tables
- **Time-limited**: a collapse timer ticks down; optional events can accelerate or delay it
- Designed for **1-6 players** entering independently or in squads of up to 3
- Host to both **PvE** and **emergent PvP** — other players are not marked as friend or foe

Extraction returns players to the Refuge with whatever they carry. Anything left behind is lost when the shard collapses.

### Content Sourcing *(Implemented)*
Shard instances load content from **PostgreSQL** content tables:
- `biome_definitions` — environmental settings, hazard types, narration hints
- `creature_definitions` — creature stats, behaviors, loot tables
- `item_definitions` — all gear and consumable items
- `room_definitions` — room templates (type, properties, hazards, loot containers)
- `loot_table_definitions` — weighted loot drop tables
- `modifier_definitions` — shard modifiers that alter run difficulty/rewards
- `narrative_template_definitions` — biome-specific narration templates

The game now supports **two shard generation modes**:
1. **Hand-crafted zones**: Designer-built room graphs stored in `zones`, `zone_rooms`, `zone_exits` tables
2. **Procedural assembly**: Rooms selected from `room_definitions` and connected algorithmically (see §10)

## 2.3 The Shard Lifecycle
1. **Seeding** — Server generates the room graph, populates loot tables, spawns creatures, places extraction nodes, and rolls shard modifiers.
2. **Open** — Entry points activate. Players may enter over a staggered window (first 5 minutes).
3. **Active** — Full exploration, combat, and extraction. Collapse timer is visible.
4. **Destabilising** — Final 25% of the timer. Environmental hazards intensify, new creature waves spawn, extraction nodes may shift.
5. **Collapse** — Shard destroys. Any player still inside loses all carried items and takes a **shard-sickness** debuff (reduced stats for the next run).

# 3. CORE GAMEPLAY LOOP

1. **Prepare**
   Select loadout from stash. Choose skills. Read the Shardboard for intel. Optionally form a squad.

2. **Enter Shard**
   Choose an entry point (different entry points land you in different parts of the graph). Spawn into a dynamically described room.

3. **Explore**
   Navigate rooms via directional commands. Read LLM-narrated descriptions. Search containers. Interpret traces and sound cues. Map mentally or with an in-game mapping item.

4. **Engage**
   Fight creatures using the action system (§5). Solve environmental puzzles. Interact with shard anomalies.

5. **Encounter**
   Detect other players via the **awareness system** (§8.1). Choose to avoid, stalk, ambush, cooperate, or trade. Communication is proximity-based.

6. **Extract**
   Locate an extraction node. Begin the **extraction ritual** — a multi-round channel that generates noise, drawing attention (creatures and players). Survive until complete.

7. **Return**
   Arrive at the Refuge. Carried items enter your stash. Gain XP. Complete any fulfilled contracts. Review the run summary.

**Death:** If you die in a shard, you drop all **non-soulbound** carried items on your corpse. Other players (or creatures) can loot it. You respawn at the Refuge with shard-sickness.

# 4. LLM NARRATIVE SYSTEM

## 4.1 Core Principle
> The LLM describes; the server decides.

The game state is fully deterministic and server-authoritative. The LLM receives a structured snapshot of what a player can perceive and returns prose. It never modifies game state, spawns items, or resolves mechanics.

## 4.2 What the LLM Generates
| Category | Examples |
|---|---|
| Room descriptions | First-entry prose, revisit summaries, darkness/light variations |
| Creature narration | Idle behaviour, threat displays, death descriptions |
| Combat feedback | Attack results, damage flavour, status effect onset |
| Environmental cues | Weather shifts, collapse tremors, hazard warnings |
| Trace descriptions | Footprints, blood trails, discarded items, sounds from adjacent rooms |
| Social | Emote embellishments, trade narration, proximity speech framing |

## 4.3 Input Schema (Authoritative State)
Each LLM call includes a structured state object. The LLM has **read-only access** to this data.

```jsonc
{
  "room": {
    "id": "shard-0a3f::room-17",
    "biome": "flooded_crypt",
    "light_level": 0.3,          // 0 = pitch black, 1 = bright
    "exits": ["north", "east", "down"],
    "features": ["collapsed_pillar", "altar_bloodstained"],
    "items_visible": [
      { "id": "item-882", "type": "weapon", "name": "corroded_halberd", "quality": 0.4 }
    ],
    "creatures": [
      { "id": "mob-44", "type": "drowned_revenant", "state": "patrolling", "hp_pct": 1.0, "disposition": "hostile" }
    ],
    "hazards": ["knee_deep_water", "unstable_ceiling"],
    "traces": [
      { "type": "footprints", "age_seconds": 180, "direction": "east", "source": "player" },
      { "type": "sound", "description": "scraping_metal", "direction": "down", "intensity": 0.6 }
    ],
    "shard_stability": 0.55       // 1 = stable, 0 = collapsing now
  },
  "player": {
    "hp_pct": 0.72,
    "statuses": ["bleeding_light"],
    "stance": "cautious",
    "awareness_level": 2,         // how much sensory detail to include
    "visited_before": false
  },
  "recent_events": [
    { "tick": 1042, "type": "combat_result", "summary": "player_hit_mob-44_slash_12dmg" },
    { "tick": 1041, "type": "sound_heard", "summary": "footsteps_east_fading" }
  ],
  "narrative_directives": {
    "tone": "dread",
    "verbosity": "standard",      // "terse" during combat, "verbose" on first entry
    "forbidden": ["reveal_hidden_items", "reveal_player_names", "invent_entities", "resolve_mechanics"]
  }
}
```

## 4.4 Output Contract
The LLM must:
- Describe **only** what is present in the state object
- Never name other players (use indirect descriptions: "a figure", "someone in dark leather")
- Never invent items, creatures, or exits that aren't in the schema
- Never state mechanical numbers (HP, damage, percentages) — translate to qualitative language ("badly wounded", "a glancing blow")
- Respect the `forbidden` array absolutely
- Stay within a token budget (configurable per call type; default ~200 tokens for room descriptions, ~80 for combat lines)

## 4.5 Caching & Performance

### LLM Provider
All narrative generation uses **GPT-4o-mini** via **Azure AI Foundry serverless endpoints** (pay-per-token, no provisioned throughput). Phase 2+ may add GPT-4o for quality-tier first-entry room descriptions; the switch is a configuration change, not an architecture change.

### The Latency Reality
GPT-4o-mini median time-to-first-token (TTFT) is approximately **1.75 seconds**. This far exceeds the 200ms combat narration target. Consequently:

> **Real-time LLM generation for every combat tick is infeasible.** The LLM is not on the hot path for combat. Caching, pre-generation, and template fallback are.

### Cache Architecture
- **Content-addressable cache**: LLM responses are cached in **Redis** keyed by the **SHA-256 hash** of the input state snapshot. Identical game states always produce the same cache key.
- **Cache scope**: Shard-specific content (room descriptions for a specific seed) has TTL = shard lifetime. Creature/biome templates have TTL = 24 hours.
- **Pre-generation**: When a player enters room N, a background task calls Foundry for all adjacent rooms. Results are cached before the player arrives.

### Narration Pipeline (per call)
1. **Hash** the state snapshot (SHA-256).
2. **Check Redis** for a cached response.
3. **Cache hit** → return cached prose immediately.
4. **Cache miss** → call Azure AI Foundry (GPT-4o-mini).
5. **Foundry responds within timeout** → deliver prose, cache the result.
6. **Foundry exceeds timeout** → fire **template fallback** (Handlebars-style templates assembled from the state object). The LLM call continues in the background; its result enriches the cache for future encounters.

### Timeout Budgets
| Context | Timeout | Fallback |
|---|---|---|
| **Combat narration** | 800ms | Template |
| **Exploration / room entry** | 2s | Template |
| **Hard limit (all contexts)** | 3s | Template + cancel Foundry call |

### Tiered Generation
| Narration Tier | Model | Token Budget | Strategy |
|---|---|---|---|
| **Combat lines** (attacks, hits, dodges) | GPT-4o-mini | ~80 output | Cache-first. Most combat states are repetitive. Pre-generate common lines during shard seeding. Template fallback for uncached. LLM enriches cache asynchronously. |
| **Room descriptions** (first entry) | GPT-4o-mini | ~200 output | Pre-generate adjacent rooms. With streaming, first tokens arrive within ~1.75s. |
| **Ambient / trace / idle** | GPT-4o-mini | ~60 output | Background generation. No urgency. Can batch multiple ambient descriptions. |

### Token Economics
```
Per LLM call (combat):   ~500 input + ~80 output  = ~$0.000123
Per LLM call (room):     ~800 input + ~200 output  = ~$0.000240
Per LLM call (ambient):  ~400 input + ~60 output   = ~$0.000096

Estimated per player-hour (with 50-70% cache hit rate):
  ~30 uncached combat calls:  $0.0037
  ~8 uncached room calls:     $0.0019
  ~10 uncached ambient calls: $0.00096
  Total: ~$0.006/player-hour
```

### Cost Control
- **Rate limiting**: Max 20 LLM calls/minute per player (server-enforced).
- **Batch API (future)**: Azure AI Foundry batch endpoints at 50% discount for pre-generation during shard seeding.
- **Fine-tuning (future)**: When enough training data exists, fine-tune GPT-4o-mini for tighter prose and smaller prompts, reducing both latency and cost.

## 4.6 Prompt Injection Defence
Player input is **never concatenated into the LLM prompt as raw text**. Player commands are parsed by the server into structured actions. If a player uses a `say` or `emote` command, their free-text speech is placed in a clearly delimited, role-separated field marked as untrusted user content and is never interpreted as an instruction.

# 5. COMMAND PARSING & ACTION SYSTEM

## 5.1 Input Model
Players type commands in a **verb-noun** syntax familiar to MUD players:

```
> go north
> look
> take corroded halberd
> attack revenant with sword
> search altar
> use bandage
> listen
> say Anyone there?
> drop torch
> extract
```

Commands are parsed **server-side** using a deterministic parser (not the LLM). The parser supports:
- Aliases and abbreviations (`n` = `go north`, `s` = `go south`, `e` = `go east`, `w` = `go west`, `l` = `look`, `i` = `inventory`, `k` = `attack`)
- Direction expansion happens in `packages/server/src/commands/parser.ts` via `DIRECTION_ALIASES` map
- Contextual disambiguation ("attack revenant" works when only one revenant is present)
- **ShardRoom** uses a modular command handler system with a Map-based registry (`packages/server/src/commands/`)
- **RefugeRoom** uses a monolithic switch statement (scheduled for unification)

Unrecognised input returns a brief error from a static template — the LLM is not invoked for bad commands.

## 5.2 Tick Model *(Implemented)*
The game runs on a **server tick** of **1 second** during combat.

- **Exploration mode**: Player commands are processed immediately on receipt via `onMessage` handlers. Creature AI ticks every 3-5 seconds (varies by creature type).
- **Combat mode**: Initiated when a hostile action occurs (e.g., `attack` command). All participants are placed on a **1-second tick**. Each player gets **one action per tick**. Actions are resolved simultaneously at tick end (see §6).
- **Transition**: Combat mode ends when no hostile entities are within interaction range for 10 seconds.

*Note: Combat implementation is basic (strike, dodge, flee). Full action variety (heavy strike, block, use item, skills) is planned but not yet implemented.*

## 5.3 Information & Visibility
What a player sees depends on:
- **Light level** of the room (affected by carried light sources, room properties, and hazards)
- **Awareness skill** (determines trace detail, sound range, and creature detection distance)
- **Stealth status** of other entities (other players, lurking creatures)
- **Line of knowledge**: Players only receive information about rooms they are currently in. No minimap. No omniscient view.

# 6. COMBAT SYSTEM

## 6.1 Philosophy *(Implemented)*
Combat is **simultaneous-resolution, tick-based, and deterministic**. It should feel tense and fast in a text medium — no walls of text per round. Each tick produces 1-3 short lines of narrated output.

The combat system is implemented in `packages/server/src/combat/CombatEngine.ts` as a pure logic class with a 1-second tick loop.

## 6.2 Actions Per Tick *(Partial Implementation)*
Each combatant chooses **one action** per tick:

| Action | Status | Notes |
|---|---|---|
| **Strike** | ✅ Implemented | Attack with equipped weapon. Resolved against target's defence. |
| **Dodge** | ✅ Implemented | Grants evasion bonus this tick. |
| **Flee** | ✅ Implemented | Attempt to leave the room. Success exits to an adjacent room. |
| **Heavy Strike** | ❌ Planned | 2-tick windup, higher damage, can stagger. |
| **Block** | ❌ Planned | Reduces incoming damage. Requires shield or parry-capable weapon. |
| **Use Item** | ❌ Planned | Consume potion, throw grenade, activate device. |
| **Skill** | ❌ Planned | Activate a skill (stamina cost). |
| **Observe** | ❌ Planned | Sacrifice action to gain detailed target info. |

## 6.3 Resolution Order
Each tick:
1. All actions are submitted (or default to `dodge` if no input received).
2. **Flee** attempts resolve first.
3. **Observe** resolves (information gathered).
4. **Dodge/Block** states are set.
5. **Strikes, Heavy Strikes, Skills, Items** resolve simultaneously.
6. Damage is applied. Status effects are applied. Deaths are checked.
7. Results are narrated by the LLM (terse mode, ~80 tokens per participant).

## 6.4 Damage Model
```
raw_damage    = weapon_base + STR_or_DEX_scaling + skill_bonus
modified_dmg  = raw_damage * stance_multiplier - target_armour
final_damage  = max(1, modified_dmg) * dodge/block_reduction
```
- Armour reduces damage linearly but degrades over the run (durability system).
- Dodge grants a % chance to fully avoid an attack (based on AGI stat + dodge skill rank).
- Block absorbs a flat amount plus a percentage (based on shield quality + STR).

## 6.5 Death & Downing
- At 0 HP, a player enters the **downed** state (10-second bleed-out timer).
- A squadmate can **stabilise** them (costs 2 ticks + a bandage item).
- If the timer expires, or a killing blow lands, the player **dies** — their corpse becomes a lootable container.
- PvE creatures do not loot corpses. Other players can.

## 6.6 Creature AI *(Partial Implementation)*
Creature definitions are stored in the `creature_definitions` table with:
- Type, name, description, behavior text
- Stats: max_hp, attack, defence, armour, agility
- Spawn rules: min_count, max_count, preferred_rooms, forbidden_rooms, idle_ticks_min/max, flee_threshold
- Biome affinity and tier range
- Loot table (JSONB)

**Planned behavior tree states:**
- **Idle** → patrol between rooms on a timer
- **Alert** → triggered by sound/proximity/traces; moves toward source
- **Hostile** → enters combat; selects actions based on archetype (berserker = strike-heavy, skulker = hit-and-flee, guardian = block-heavy)
- **Fleeing** → low HP creatures may retreat, potentially leading players into ambushes

*Note: Creature definitions exist in the database; full AI behavior trees are not yet implemented. Current creatures use basic combat logic.*

# 7. PROGRESSION & CHARACTER BUILD

## 7.1 No Classes, Only Skills *(Database Foundation Implemented)*
There are no fixed classes. Characters are defined by the **skills they invest in** and the **gear they bring**.

Skills are stored in the `skill_definitions` table (slug, name, description, category, cooldown_ticks, stamina_cost, effects JSONB, requirements JSONB). Player skill progression is tracked in the `player_skills` table (skill_name, category, level, xp).

### Skill Categories
| Category | Examples | Governs |
|---|---|---|
| **Combat** | Swordsmanship, Marksmanship, Unarmed, Heavy Weapons | Damage scaling, special strikes, weapon proficiency |
| **Defence** | Armour Training, Evasion, Shield Mastery | Damage reduction, dodge chance, block efficiency |
| **Survival** | First Aid, Trapping, Foraging, Shard Attunement | Healing, crafting field items, extending collapse timers |
| **Subterfuge** | Stealth, Lockpicking, Pickpocket, Sabotage | Avoiding detection, accessing locked containers, disabling traps |
| **Awareness** | Tracking, Listening, Shard Sense, Appraisal | Trace detail, sound range, detecting hidden entities, identifying item quality |
| **Social** | Intimidation, Barter, Leadership | PvP negotiation bonuses, trade prices, squad buff radius |

### Advancement *(Planned, Not Implemented)*
- Skills level through **use** (swing a sword → Swordsmanship XP). No grinding mobs at a safe spot: XP is only granted during shard runs and scales with shard tier.
- A **soft cap** system: each skill has diminishing returns past certain thresholds. Hitting cap in one area is fast; being a generalist is viable but slower.
- **Respec** is possible but costly (rare consumable or faction service). Encourages commitment but not permanent regret.

*Note: Skill system tables exist, but skill progression mechanics (XP gain, leveling, effects) are not yet fully implemented.*

## 7.2 Gear *(Database-Driven)*
- Gear is **the primary source of power** in any given run. Skills determine the *ceiling* of what you can use effectively; gear determines your actual stats.
- All items are stored in the `item_definitions` table with type (weapon, armour, consumable, material, tool, key, blueprint), tier (scrap, common, sturdy, refined, masterwork, anomalous), stats JSONB, and durability settings.
- All gear has **durability** that depletes during a run. Repair mechanics are planned but not yet fully implemented.
- Gear tiers: **Scrap → Common → Sturdy → Refined → Masterwork → Anomalous**. Higher tiers are correspondingly rarer and more painful to lose.
- **Soulbound items** exist (soulbound flag in DB) but are rare (quest rewards, seasonal achievements). They are not dropped on death.

*Note: Item definitions exist in the database; full durability/repair mechanics are not yet implemented.*

## 7.3 Stash & Loadout *(Implemented)*
- The **stash** is persistent storage in the Refuge, stored in PostgreSQL (`player_stash` table). It uses a **weight-based capacity system** (default 200 weight units, expandable via upgrades in `player_stash_capacity` table).
- Stash is accessed in the **Stash Alcove** room via `stash`, `take <item>`, and `store <item>` commands.
- A **loadout** is equipment you wear into a shard, stored in **equipment slots**: weapon, offhand, head, chest, legs, feet (`player_loadout` table). Managed via `equipment` and `loadout` commands.
- Each item has **durability** that degrades during runs and can be repaired using materials.
- Anything in your loadout that isn't extracted is **lost forever** (except soulbound items).

## 7.4 Characters *(Implemented)*
Players can create **multiple characters** per account (1:N relationship):
- Each character has its own name, faction affiliation, skills, stash, and loadout
- Character data is stored in the `characters` table with soft-delete support (`deleted_at` column)
- Only **one character can be active** per account at a time (`is_active` flag)
- Character creation and selection UI is implemented in the React client
- All player progression (skills, stash, factions, run history) is linked to `character_id`, not `player_id`

# 8. PvP SYSTEM *(Planned, Foundation Exists)*

## 8.1 Awareness & Detection *(Not Implemented)*
PvP is **always possible** inside a shard — there is no opt-out, safe zone, or flagging system. This is core to the extraction tension. However, encountering another player is **not instant or obvious**:

1. **Sound propagation**: Actions generate sound values. Loud actions (combat, breaking doors) propagate through adjacent rooms (attenuated by distance and room properties). Players with high **Listening** skill hear more.
2. **Traces**: Players leave traces — footprints, blood, discarded items, opened containers. The Tracking skill reveals age and direction. Traces decay over time.
3. **Room entry**: When another player is in your room, you receive a description based on **their stealth vs your awareness**:
   - **High stealth, low awareness**: No indication.
   - **Moderate match**: "You sense you are not alone." / "A shadow shifts near the eastern wall."
   - **Low stealth or high awareness**: Full detection — "A figure in battered chainmail stands near the altar, a blade in hand."

4. **Identification**: Players are **never identified by name** in shard narration. You see descriptions based on their visible equipment. You can only confirm identity through direct communication (`say`, `whisper`).

## 8.2 Engagement Rules
- Any player can **attack** any other player at any time. No confirmation prompt.
- Attacking initiates combat mode for all participants in the room.
- There is **no alignment or karma system**. The game does not morally judge PvP.

## 8.3 Stakes
- On death, the victim drops **all non-soulbound items** as a lootable corpse.
- The killer receives no XP for PvP kills (prevents farming).
- The victim suffers **shard-sickness** (see §2.3).
- Repeated deaths in a short window intensify shard-sickness (diminishing returns on back-to-back risky runs — not punitive, but encourages loadout thought).

## 8.4 Cooperation & Betrayal
- Squads (up to 3) can enter together. Friendly fire is **on** — there is no squad immunity.
- Temporary truces with strangers are possible through `say` communication. Nothing enforces them.
- Players can **trade** items in the same room (`offer <item> to <target>`). Trades require mutual confirmation.
- This design space intentionally enables betrayal, negotiation, and emergent alliances.

## 8.5 Anti-Griefing
While PvP is unrestricted, structural design discourages pure griefing:
- Entry points are spread across the shard graph — players don't spawn-camp.
- Shard keys cost resources — entering a shard just to hunt under-geared players is economically negative.
- No name identification means no targeted harassment across runs.
- Staggered entry windows mean you don't know how many players are in the shard or where they spawned.

# 9. ECONOMY & FACTIONS

## 9.1 Currency & Resources *(Planned)*
There is **no universal currency**. The economy runs on **barter and materials**:

| Resource | Source | Use |
|---|---|---|
| **Shardsteel** | Salvaging weapons/armour from shards | Crafting, repairing gear |
| **Echo Dust** | Creature drops, environmental harvesting | Consumable crafting, shard key creation |
| **Anomalous Fragments** | Rare shard events, high-tier creatures | Masterwork/Anomalous gear crafting, faction projects |
| **Shard Keys** | Crafted from Echo Dust + Faction recipe | Required to enter a shard |
| **Blueprints** | Loot, quest rewards, faction rank-ups | Unlock new crafting recipes (consumed on learn) |

## 9.2 Crafting *(Planned)*
- Crafting stations are in the Refuge, gated by **faction membership**.
- Recipes require materials + a learned blueprint + a skill check (Survival or relevant crafting skill).
- Output quality varies based on skill level and material quality — slight randomness within a range.
- No crafting XP grind: crafting skill improves alongside Survival, which levels during shard runs.

## 9.3 Trading *(Planned)*
- **Direct trade**: Two players in the Refuge can open a trade window (text-based offer/counter-offer/confirm).
- **Marketplace**: A faction-run bulletin board. Players post offers (item for item/materials). Listings expire after 24 hours. A small listing fee (Echo Dust) prevents spam.
- No auction house / no gold. Prices are emergent and player-determined.

## 9.4 Factions *(Database Foundation Implemented, Mechanics Planned)*
Three factions are defined in the `factions` table with name, slug, philosophy, and specialty fields. The `faction_membership` table tracks player affiliations with reputation and rank columns.

Three factions compete for influence over shard access and world events:

| Faction | Philosophy | Specialty |
|---|---|---|
| **The Ironwright Compact** | Pragmatic survivalists. Gear and craftsmanship above all. | Best crafting recipes, armour bonuses, durability perks. |
| **The Veil Cartographers** | Knowledge-seekers. Map the shards, understand the collapse. | Awareness bonuses, extended shard timers, anomaly detection. |
| **The Scarlet Ledger** | Risk-takers and profiteers. High risk, high reward. | Better loot rolls, PvP stealth bonuses, black-market access. |

### Faction Mechanics *(Planned)*
- **Reputation** is gained through contracts, donating materials, and achieving faction objectives.
- **Rank** unlocks crafting recipes, faction gear, and passive perks.
- Players can only belong to **one faction** at a time. Switching is possible but resets reputation to zero.
- **World events**: When a faction collectively donates enough resources, they unlock a **special shard** — a limited-time, high-difficulty instance with unique loot.

*Note: Faction tables exist in the database; reputation gain, rank progression, crafting unlocks, and world events are not yet implemented.*

# 10. SHARD GENERATION & ZONE SYSTEM

## 10.1 Zone System Overview *(Implemented)*
Ellmud uses a **database-driven zone system** that supports both hand-crafted persistent zones and dynamically generated shard instances.

### Database Schema
Zones are defined in three core tables:
- **`zones`** — Zone metadata (slug, name, tier, biome, lifecycle, category, max_players, pvp_enabled)
- **`zone_rooms`** — Rooms within a zone (slug, name, type, properties, hazards, NPCs, loot_containers)
- **`zone_exits`** — Directional connections between rooms (from_room_slug → direction → to_room_slug)

### Zone Types
| Category | Examples | Lifecycle | Use Case |
|---|---|---|---|
| **hub** | The Refuge | `persistent` | Safe zone, feature rooms, long-lived |
| **dungeon** | Hand-crafted shard zones | `persistent` or `scheduled` | Designer-built encounters |
| **wilderness** | Open exploration zones | `persistent` | Future: open-world areas |
| **social** | Faction headquarters | `persistent` | Future: faction-specific hubs |

### Inter-Zone Travel
The `zone_exits` table supports connections between zones:
- **Intra-zone exits**: `from_room_slug → direction → to_room_slug` (same zone)
- **Inter-zone exits**: `target_zone_slug` + `target_room_slug` (cross-zone travel)
- Locked/hidden exits supported via `locked` and `hidden` boolean flags

## 10.2 Room Graph Topology (Shard Instances)
Shard instances can be generated in two ways:

### Mode 1: Hand-Crafted Zones *(Implemented)*
Designers create zones in the database via the **admin dashboard**. The zone management view allows:
- Creating zones with metadata (name, tier, biome, lifecycle, PvP settings)
- Defining rooms (type: entry, corridor, chamber, boss, extraction)
- Connecting rooms with directional exits
- Setting room properties, hazards, NPCs, loot containers

Shard instances using hand-crafted zones load the complete room graph from the database at runtime.

### Mode 2: Procedural Assembly *(Partial Implementation)*
Shards can also be generated procedurally by:
1. Selecting a **seed** (determines all procedural outcomes for reproducibility)
2. Choosing rooms from the `room_definitions` table based on biome and tier
3. Algorithmically connecting rooms into a graph with anchor points (entry, extraction, boss, treasure)
4. Adding **dead ends** and **loops** for non-trivial navigation
5. Placing **locked doors** and **barriers** that require keys or actions to pass

### Graph Size by Tier
| Shard Tier | Rooms | Entry Points | Extraction Nodes | Player Slots |
|---|---|---|---|---|
| Tier 1 (Shallow) | 15-25 | 2 | 2 | 1-3 |
| Tier 2 (Deep) | 25-40 | 3 | 2-3 | 2-4 |
| Tier 3 (Abyssal) | 40-60 | 4 | 2-3 | 3-6 |

## 10.2 Biomes *(Database-Driven)*
Each shard has a **primary biome** stored in the `biome_definitions` table. Biome records include:
- **Slug** and **name** (e.g., `flooded_crypt`, "Flooded Crypt")
- **Description** (atmospheric lore text)
- **Tier** (difficulty level)
- **Features** (array of environmental descriptors)
- **Hazard types** (array of possible environmental dangers)
- **Room properties** (array of room characteristics)
- **Narration hints** (array of atmospheric keywords for LLM prompts)

Biomes determine room templates, creature pools, and environmental hazards. Content designers manage biomes via the **admin dashboard**.

| Biome | Flavour | Signature Hazard | Signature Creature |
|---|---|---|---|
| **Flooded Crypt** | Waterlogged tombs, dripping stone | Rising water (room floods over time, reducing actions) | Drowned Revenants |
| **Shattered Bastion** | Broken fortress, collapsed walls | Unstable ceilings (cave-ins on loud actions) | Ironbound Sentinels |
| **Fungal Deep** | Bioluminescent caverns, spore clouds | Toxic spores (poison ticks without a mask) | Sporeweavers |
| **Ember Rift** | Volcanic fissures, obsidian tunnels | Heat waves (stamina drain) | Cinder Wraiths |
| **Hollow Archive** | Ruined library, whispering stacks | Psychic resonance (confusion/disorientation) | Ink Horrors |

*Note: Current implementation has biome definitions in the database, but full environmental hazard mechanics are not yet implemented.*

## 10.3 Shard Modifiers *(Database-Defined, Mechanics Planned)*
Shard modifiers are stored in the `modifier_definitions` table with:
- **Slug** and **name** (e.g., `dense`, "Dense")
- **Description** (explains the modifier's effect)
- **Effects** (JSONB field with mechanical parameters)
- **Stackable** (boolean — can multiple modifiers of this type apply?)
- **Tags** (array for filtering/categorization)

Each shard can roll 1-3 **modifiers** that alter the run:

| Modifier | Effect |
|---|---|
| **Dense** | +30% room count, +20% loot |
| **Hunted** | A roaming elite creature stalks the shard |
| **Silent** | Sound propagation halved — harder to detect players and creatures |
| **Fractured** | Some room connections break partway through (paths become one-way or close entirely) |
| **Bountiful** | Loot quality increased by one tier across the board |
| **Cursed** | All players take slow, passive damage; healing items are 50% less effective |
| **Mirrored** | Layout is symmetric — useful info for navigation but also for predicting other players' paths |
| **Dark** | Global light level reduced to 0.1; torches are critical |

*Note: Modifier definitions exist in the database; runtime modifier application mechanics are not fully implemented.*

## 10.4 Loot Distribution *(Database-Driven)*
- Loot spawns are determined by **loot table definitions** (`loot_table_definitions` table) which contain weighted entries for item drops.
- **Loot tiers** scale with shard tier and room danger (rooms closer to boss rooms or behind locks have better loot).
- All items are stored in the `item_definitions` table (name, type, tier, stats, durability, soulbound flag).
- Containers types include: crates (common), locked chests (require Lockpicking or keys), altars (require Shard Attunement), corpses of previous failed Shardwalkers (environmental storytelling — not real player corpses, procedurally placed).
- Creatures drop loot on death from loot tables defined in `creature_definitions.loot_table` (JSONB field).

# 11. TRACE SYSTEM *(Planned, Not Implemented)*

## 11.1 Definition
**Traces** are persistent environmental marks left by player and creature actions inside a shard. They are the primary source of indirect information about other entities — the "footprints in the snow" of the game.

## 11.2 Trace Types

| Trace | Left By | Information Conveyed |
|---|---|---|
| **Footprints** | Movement | Direction of travel, approximate time, weight class (light/heavy gear) |
| **Blood trail** | Taking or dealing damage | Direction, severity (drips vs smears) |
| **Opened container** | Searching/looting | Someone has been here; container is empty or partially looted |
| **Broken door/lock** | Forced entry | Strength vs finesse (smashed vs picked), time |
| **Corpse** | Killing a creature | What creature, how it died, approximate time |
| **Discarded item** | Intentional drop or inventory overflow | The item itself + location |
| **Sound echo** | Loud actions (combat, explosions) | Direction, distance (rooms away), intensity |
| **Residue** | Skill/item use (potions, traps, abilities) | Type of residue, freshness |

## 11.3 Trace Decay
All traces have a **time-to-live (TTL)** measured in game ticks:
- Footprints: 300s
- Blood: 600s
- Sound echoes: immediate (heard in real time, not persistent)
- Container state: permanent for the shard's lifetime
- Corpses: permanent

## 11.4 Interaction with Skills
- **Tracking** skill increases the detail of trace descriptions (e.g., without Tracking, you see "footprints lead east"; with high Tracking, you see "fresh boot prints, heavy-shod, heading east — perhaps two minutes old").
- **Stealth** skill reduces the traces a player leaves (lighter footprints, no blood trail below certain damage thresholds).
- The LLM communicates trace information narratively based on the player's awareness level — the server decides what you *can* know, the LLM decides how to *say* it.

# 12. SOUND SYSTEM *(Planned, Not Implemented)*

## 12.1 Purpose
Sound is the primary medium for **cross-room awareness**. In a text game without a visual viewport, sound replaces "seeing someone in the distance."

## 12.2 Mechanics
- Every action has a **noise value** (0 = silent, 10 = deafening).
- Noise propagates room-by-room, attenuating by **2 per room** traversed. If `noise - (2 * rooms_away) > 0`, the sound is audible.
- Room properties modify propagation: heavy doors halve noise, open caverns add +1 range, water carries sound further.
- The **Listening** skill lowers the audibility threshold (effectively increasing hearing range).

### Example Noise Values
| Action | Noise |
|---|---|
| Walking | 2 |
| Running | 4 |
| Combat (melee) | 5 |
| Breaking a door | 7 |
| Explosion (grenade) | 9 |
| Extraction ritual | 8 (sustained for duration) |
| Sneaking | 0 (with Stealth skill) to 1 (without) |

## 12.3 Information Conveyed
Sounds deliver **directional** ("from the north-west") and **qualitative** ("distant clash of metal", "someone running") information. They never identify players by name or give exact room locations.

## 13.2 Server Authority
- All game state lives on the **Game Server**. The client is a dumb terminal.
- Player commands are validated server-side. Invalid or impossible commands are rejected before any state change.
- Random outcomes use a seeded PRNG per shard — deterministic, replayable, auditable.

## 13.3 Colyseus Room Architecture

### Room ↔ Instance Mapping
Each Colyseus Room maps 1:1 to a game instance:

| Room Type | Lifecycle | Purpose |
|---|---|---|
| **`ShardRoom`** | Ephemeral (20-40 min) | One shard instance. Holds room graph, creature state, player positions, loot, timers. Created at shard seeding, disposed at collapse. |
| **`RefugeRoom`** | Long-lived | The persistent hub zone. Handles navigation between feature rooms (stash, shardboard, market, etc.). Loads zone structure from database (`zones`, `zone_rooms`, `zone_exits` tables). |

### Message-Only Client Protocol
The client communicates exclusively via Colyseus messages. **Schema state sync is server-internal only — it is never sent to game clients.**

```
┌─────────────┐         WebSocket (Colyseus)         ┌──────────────────┐
│  Web Client  │ ◄──── "narrate" messages (prose) ──── │   ShardRoom       │
│  (@colyseus/ │ ────► "cmd" messages (verb-noun) ───► │   (server-auth)   │
│   sdk)       │                                       │                   │
│              │                                       │  Schema State     │
│  Ignores     │         ┌──────────────┐              │  (rooms, mobs,    │
│  state sync  │         │  LLM Service │◄─── state ───│   items, traces)  │
│              │         │  (Foundry)   │───► prose ──►│   SERVER-ONLY     │
└─────────────┘         └──────────────┘              └──────────────────┘
```

**Why this pattern:**
- Clients send commands via `room.send("cmd", { verb: "attack", target: "revenant", instrument: "sword" })`.
- Server resolves the command, builds a per-player state snapshot, generates narration (cached, LLM, or template), and delivers prose via `client.send("narrate", { text: "..." })`.
- Schema state is retained internally for change tracking, serialisation, snapshot/restore, and **admin dashboard visibility** (see below).
- **State leakage to clients is the critical failure mode.** Enforced via: custom client wrapper that ignores Schema patches, integration tests asserting no Schema-type messages reach the client, and code review gates.

### Client SDK
The web client is built with **React 18 + Vite** using the **`@colyseus/sdk`** package. The client:
- Uses only the message channel (`room.onMessage`) and ignores all state synchronisation
- Renders text in a styled terminal interface with TailwindCSS and shadcn/ui components
- Provides a **compass navigation control** (3×3 directional grid) for intuitive movement
- Displays two distinct layouts:
  - **Shard Exploration**: 2-column layout (70% narrative panel + 30% combat/status sidebar)
  - **Refuge**: 3-column tab-based layout (left sidebar with compass, center content tabs, right ambient events/chat)
- Handles **direction aliases client-side** for UI prediction, though server-side parsing is authoritative
- Supports reconnection token infrastructure for graceful handling of brief network drops

The SDK's reconnection infrastructure is worth the unused state-sync weight.

### Admin Dashboard
The admin/debug dashboard is designed from day one to use **Colyseus Schema sync** — the only authorised consumer of live Schema state. This enables real-time inspection of shard state (room graphs, creature positions, player inventories, tick budgets) without custom tooling.

### Tick Model
`setSimulationInterval(callback, 1000)` — a 1-second server tick — runs in every Room:

| Mode | Behaviour |
|---|---|
| **Exploration** | Tick handles background systems: creature AI (patrol, alert), trace decay, collapse timer countdown, sound propagation. Player commands are processed immediately in `onMessage` handlers. |
| **Combat** | Tick additionally collects player actions during the tick window and resolves them simultaneously at tick boundary. No input received = default to `dodge` (see §6.3). |
| **Refuge** | Tick handles room navigation and zone state. *Future: Will drive ambient world simulation (NPC movement, weather cycles, faction events, merchant schedules).* |

### Horizontal Scaling
- **Redis presence** (unmanaged Redis container) tracks which Colyseus process owns which Room. Wired from day one even in single-replica Phase 1 to avoid rework.
- Multi-replica scaling via **KEDA auto-scaling** in Container Apps. WebSocket sticky sessions ensure subsequent messages route to the correct replica.
- Phase 2+: Separate matchmaker process via Colyseus `isStandaloneMatchMaker`.

```

    ↓

    ↓
```

Repositories following this pattern:

When `DATABASE_URL` is set, the Provider returns the PostgreSQL implementation. Otherwise, it returns the in-memory implementation (useful for local development without a database).

The admin dashboard is the **only authorised consumer** of Colyseus Schema state sync. This enables real-time inspection of shard state (room graphs, creature positions, player inventories, tick budgets) without custom tooling.

## 13.6 LLM Integration
- The LLM service calls **Azure AI Foundry GPT-4o-mini serverless endpoints** (pay-per-token, no provisioned throughput).
- Request priority: combat narration > room entry > idle/ambient.
- The LLM is **never on the hot path** for combat. Cache-first, template fallback, LLM enriches cache asynchronously (see §4.5 for full pipeline).
- Budget: ~800ms timeout for combat lines, ~2s for room descriptions. Hard timeout at 3s — fallback to templates. Gameplay is never blocked.
- **Cost control**: Aggressive caching (content-addressable by SHA-256 state hash in Redis), pre-generation of adjacent rooms, rate limiting per player per minute (~$0.006/player-hour at 50-70% cache hit rate).

## 13.7 Networking
- **Protocol**: WebSocket only, via Colyseus transport. No SSH or raw TCP support.
- **Client**: Web browser with `@colyseus/sdk`. No alternative clients.
- **Reconnection**: `allowReconnection(client, 30-60s)` provides graceful handling of brief network drops. During the reconnection window, the disconnected player's character defaults to `dodge` in combat (matches §6.3 no-input default).
- **Tick sync**: In combat, the server sends a prompt at tick start and expects a response within the tick window. No response = default to `dodge`.
- **Latency tolerance**: The text medium is inherently more latency-tolerant than a real-time action game. 200ms round-trip is comfortable. 500ms is acceptable.
- **Custom domain**: `kirbytoso.xyz` (owned), configurable on Container Apps.

# 14. ANTI-CHEAT & INTEGRITY

- **Server-authoritative**: The client never decides outcomes. There is no client-side prediction to exploit.
- **Input validation**: Commands are parsed into a fixed action set. Freeform text only exists in `say`/`emote` — it cannot influence game state.
- **Seeded PRNG**: All random outcomes can be replayed and verified.
- **Rate limiting**: Command input is capped per second to prevent automation advantage.
- **Obfuscated output**: The client receives only narrated prose via `room.send("narrate")` — never raw game state or Schema patches. A bot would need to parse natural language to extract actionable information, which is significantly harder than parsing structured data.
- **Behavioural detection**: Abnormal command-timing patterns (inhuman consistency, zero reaction time) trigger review flags.

---

# 15. ACCESSIBILITY

- **Screen reader compatibility**: All output is structured text. No reliance on colour alone — status effects and alerts are conveyed through word choice.
- **Colour as enhancement only**: ANSI colour is used for emphasis (red = danger, green = safe, yellow = caution) but all information is readable without colour.
- **Configurable verbosity**: Players can set the LLM to terse, standard, or verbose mode, controlling how much prose they receive per event.
- **Command aliases**: Fully customisable alias system so players can map commands to whatever is comfortable.
- **Pause on prompt** (solo mode): In single-player shards (Tier 1 only), players can pause the tick system. Not available in multiplayer shards.

# 16. MONETISATION (if applicable)

If the game uses a monetisation model, it adheres to these principles:
- **No pay-to-win.** Purchasable items are **cosmetic text themes** (different narration styles — gothic, noir, clinical, humorous) and **convenience** (extra stash tabs, cosmetic titles).

# 18. OPEN QUESTIONS

These are deliberate design questions to resolve through playtesting:

1. **Solo viability at high tiers.** Should Tier 3 shards require a squad, or should a skilled solo player always have a path?
2. **PvP loot drop amount.** Drop all non-soulbound (punishing) vs drop a percentage (forgiving)? Needs testing for how it affects player willingness to bring good gear.
3. **Shard collapse strictness.** Is shard-sickness enough of a penalty, or should collapse = full inventory loss + sickness?
4. **LLM model economics.** At ~$0.006/player-hour (50-70% cache hit rate) with GPT-4o-mini, costs are manageable through Phase 1. At what player count does the linear scaling of uncached calls become prohibitive? Fine-tuning and batch API pricing (50% discount) are levers for Phase 2+.
5. **Squad size.** Is 3 the right cap? Does duo-vs-duo produce better emergent encounters than trio-vs-solo?
6. **Extraction ritual duration.** Too short = no tension. Too long = feels tedious. Needs iteration.
7. **Trace system fidelity.** How much trace information is "fun espionage" vs "overwhelming noise"?
8. **Communication meta.** Will players just use Discord to bypass in-game proximity chat? Does that matter, or does it only help squads (who'd coordinate externally anyway)?
